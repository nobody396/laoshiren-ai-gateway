# 链动小铺原生结账运行手册

## 目标与边界

原生结账让已登录用户在老实人AI站内选择商品、扫描链动小铺当前启用的微信或支付宝付款码，并在支付完成后自动获得权益。链动小铺负责收款和发卡；老实人AI数据库负责账号级限购、订单幂等、卡密校验和自动兑换。

首个试点为 `trial-balance-1-to-5`：实付 ¥1，发放 ¥5 **纯赠送额度**，每个账号终身仅一次。对应链动商品 ID `746430`、goods key `oc3w4r`，保持 `show=0`，不在小铺目录公开。

## 安全不变量

- 只使用当前登录账号的注册邮箱下单；订单表仅保存域隔离的 HMAC，不复制邮箱正文。
- `native_checkout_orders` 的部分唯一索引是每账号一次的唯一权威。不要开启链动侧按 IP/联系方式限购，因为所有买家请求来自同一服务端出口。
- 支付后必须同时校验交易号、商品 key、联系方式、数量、实付金额、发货数量和卡密权益。
- 试点卡必须为 `type=balance`、`value=5`、`paid_value=0`、`purpose=gift`、`sales_status=gifted`、`validity_days=0`。
- 已上传链动的原生结账库存必须预先登记到 `native_checkout_redeem_inventory`。公开手动兑换接口会拒绝这些卡，只有已绑定订单的站内履约路径可兑换。
- 即使付费订单是在原生订单表之外恢复，只要对应原生库存卡已由该账号使用，也必须计为该账号已领取一次，不能重新开放购买按钮。
- 不记录完整卡密、注册邮箱、付款 URL 或链动交易号到日志。
- 下单时只接受链动返回的 `WeixinNative` 或 `Alipay` 活跃扫码通道，并把实际选中的通道固化为订单的 `payment_method`。前端必须按订单值提示“打开微信扫码”或“打开支付宝扫码”，不得从商品当前配置或付款 URL 猜测。
- 付款状态由服务端与浏览器轮询自动确认；链动官方买家前端也是每 3 秒查询 `/shopApi/Pay/query`，当前未发现可配置的可靠付款 Webhook。站内不让关闭支付弹窗的空闲页面继续高频查询，10 分钟建议窗口后降为 15 秒一次，后台每 15 秒兜底。
- 匿名 `/shopApi/Order/info` 详情稍后可能要求买家重新输入联系方式并通过人机验证。生产必须通过部署 secret 注入 `LDXP_MERCHANT_USERNAME` / `LDXP_MERCHANT_PASSWORD`，使后台在匿名详情不可用时自动改走商户订单详情；商户 token 仅在进程内缓存。匿名详情或商户接口出现 403/429 时必须熔断 10 分钟，不能形成重试风暴。
- 链动创建订单响应与订单详情目前都不返回明确失效时间。前端只能显示“建议 10 分钟内支付”，并明确实际有效期以微信/支付宝付款页为准；不得把建议窗口冒充支付渠道失效倒计时。

## 发布门

商品目录展示只读本地 offer，避免每次打开充值页都请求链动。真正下单前仍会重新校验商品状态、金额、联系方式格式和实际支付通道；校验失败不会返回可付款订单。因此代码合并或应用部署不等于开售。

开售前依次确认：

1. 数据库迁移成功，试点 offer 唯一索引存在。
2. `native_checkout_redeem_inventory` 中未分配库存数与链动商品库存精确一致。
3. 链动商品仍为 ¥1、邮箱联系方式、隐藏展示、链动侧限购为 0，且微信 Native 或支付宝扫码渠道至少有一个可用。
4. 应用健康与鉴权边界正常后，再将链动商品设为 `status=1`，保持 `show=0`。
5. 使用测试账号完成一次真实小额支付，确认站内自动到账 ¥5 赠送额度，第二次点击不新建订单。
6. 等待匿名订单详情要求重新查询后，验证商户 API 兜底仍能取得同一张卡并幂等完成；正常支付并发卡后预计 3–15 秒到账。

任一校验失败，立即将链动商品设为 `status=0`。新下单会在链动预检处失败；不要删除订单或库存记录。

## 补库存

补货必须使用新的稳定批次引用生成纯赠送卡，先将全部 code ID 和 offer 原子登记到 `native_checkout_redeem_inventory`，精确回读后才可上传链动。禁止先上传再登记，也禁止把完整卡密写入仓库、日志或聊天。当前试点 10 张库存耗尽前，应先补充受控的“生成 + 登记 + 上传 + 回读”运维命令，不要手工补货。
