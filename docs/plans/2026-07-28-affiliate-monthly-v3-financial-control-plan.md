# 老实人 AI 联盟计划与新月卡 V3：资金安全实施与审查稿

> 日期：2026-07-28
> 状态：资格规则已于 2026-07-30 更新，实施中；本文不授权生产发布
> 适用开发分支：`feat/affiliate-program-v2-20260726`
> 隔离验收环境：`http://127.0.0.1:18080`
> 生产边界：代码、卡密、数据库、联盟开关、现金打款均不得因为本文自动进入生产

## 1. 一句话目标

在不收加盟费、不做多级抽成、不让同一笔钱重复返佣的前提下，建立两条互斥轨道：

1. 普通用户首笔实付：邀请人与被邀请人各得 5% 平台额度；
2. 合伙人直属客户真实消费：固定 10% 分润池，由客户返利和合伙人现金佣金动态分配。

同时推出只限制月度总额度的 `Plus / Pro / Max` 三档月卡，并在完整考虑店铺费、最高联盟负担、佣金转额度增益和当前最坏已观测成本后，守住不低于 35% 的压力毛利率。

---

## 2. 不可破坏的资金原则

以下规则必须同时由数据库约束、事务和测试保护，不能只靠前端：

1. **一笔真实付费只能进入一个奖励池。**
2. **每笔符合条件的消费最多只有一个直属合伙人，不递归向上分润。**
3. **本人不能从自己的充值或消费中取得佣金。**
4. **赠送、补偿、测试、迁移、佣金转换所得额度永不产生联盟奖励。**
5. **所有金额使用整数微单位或分，禁止浮点数参与入账。**
6. **所有奖励、消费确认、提现和冲销必须有唯一业务键，重复请求不得重复入账。**
7. **账本只追加，不删除历史资金记录；错误使用反向分录修正。**
8. **生产旧数据不回填；只计算联盟正式启用后的新业务事件。**
9. **当前周期的月卡额度和计费表版本锁定，不能追溯减损。**
10. **任何配置修改如果会让压力毛利率低于 35%，后端必须拒绝保存。**

### 2.1 金额精度与舍入

- 数据库统一使用 `BIGINT micros`，人民币、现金佣金和 `⚡` 都不使用浮点数；
- 百分比分配统一向下取整到最小记账单位；
- 同一个 10% 池先计算总池，再拆成客户份额和合伙人份额，禁止两边分别四舍五入后超过总池；
- `¥1 -> ⚡1.2` 使用整数比例 `6 / 5` 计算；
- 不能整除的尾差留在平台舍入账户，并在每日对账中单列；
- 前端最多显示两位小数，但显示精度不能反过来成为账本精度。

## 4. 永久直属关系

### 4.1 绑定规则

- 一个用户只能有一个直属邀请人；
- 绑定成功后不可自行更改；
- 禁止自己邀请自己；
- 注册事务必须同时完成“创建用户 + 绑定邀请关系”，不能先创建用户再异步补绑；
- OAuth 跳转前把邀请凭证写入签名、短期、同站 Cookie；OAuth 成功后消费并清除；
- 邀请码不存在、已停用、过期或指向本人时，不建立关系；
- 所有绑定保存邀请链接版本和返利比例快照。

### 4.2 防环

绑定时检查：

- `inviter_user_id != customer_user_id`；
- 邀请人不能已经是当前用户的下级；
- 数据库维护唯一直属边，禁止形成 `A -> B -> A` 或更长环路。

## 5. 普通用户首笔实付奖励

### 5.1 规则

邀请人仍是普通用户时，被邀请人完成第一笔符合条件的真实付费：

- 邀请人：首笔实付金额的 `5%⚡`；
- 被邀请人：首笔实付金额的 `5%⚡`；
- 两者均 T+0；
- 无最低金额；
- 无固定 `⚡5`；
- 无 T+1；
- 每个被邀请用户终身只触发一次。

### 5.2 合格来源

可以触发：

- 实售余额卡兑换；
- 实售月卡兑换；
- 以后接入的、可核验真实支付的直接充值。

不能触发：

- 礼品卡；
- 补偿卡；
- 测试卡；
- 迁移卡；
- 管理员赠送；
- 客户返利；
- 普通邀请奖励；
- 佣金转平台额度。

### 5.3 防重复

首笔实付使用唯一键：

```text
first-paid:{customer_user_id}
```

同一事务内：

1. 锁定首付资格；
2. 写入实付事件；
3. 给邀请人与被邀请人各写一笔 5% 奖励；
4. 给奖励生成 `affiliate_eligible=false` 的余额批次；
5. 标记该首付来源已经消耗过联盟奖励池。

任何步骤失败，整个事务回滚。

## 6. 合伙人申请与人工审核

达到任一路线只代表“可以申请”，绝不自动成为合伙人。

### 6.1 路线 A：直属团队

同时满足：

- 5 名有效直属用户；
- 每人累计确认真实消费至少 ¥20；
- 达到单人门槛的有效直属用户累计确认真实消费至少 ¥1,000。

### 6.2 路线 B：本人消费

- 申请人本人累计确认真实消费至少 ¥500；
- 不要求邀请用户，直属用户消费不计入路线 B。

路线 B 只给予提交申请的资格，不自动开通现金分润。平台仍进行人工审核；申请人的本人消费永远不会给本人产生佣金。

### 6.3 人工审核

管理员检查：

- 直属客户与消费是否真实；
- 是否存在同设备、同支付身份、同收款身份、批量注册等风险；
- 推广内容是否存在夸大收益、承诺躺赚等问题；
- 用户状态是否正常；
- 是否接受合伙人规则、隐私说明和税务处理说明。

审核状态：

```text
未达标 -> 可申请 -> 审核中 -> 已开通
                       \-> 未通过
```

前端不能把达到门槛描述成“自动获得现金佣金资格”。

## 7. 合伙人 10% 动态分润池

### 7.1 核心公式

每笔直属客户的合格确认消费只产生一个 10% 池：

```text
客户平台额度返利率 = r，0% <= r <= 10%
合伙人现金佣金率   = 10% - r
```

按 1% 调整，默认 `r = 5%`。

| 客户返利 | 客户获得 | 合伙人现金 |
| ---: | ---: | ---: |
| 0% | 0%⚡ | 10% |
| 3% | 3%⚡ | 7% |
| 5% | 5%⚡ | 5% |
| 8% | 8%⚡ | 2% |
| 10% | 10%⚡ | 0% |

### 7.2 比例快照

- 客户注册绑定时锁定链接的比例版本；
- 合伙人以后调整链接，只影响后来绑定的客户；
- 不追溯降低或提高老客户比例；
- 默认链接永久存在，不能删除；
- 最多额外创建 5 个渠道链接；
- 每个渠道链接都能独立调整 0%–10%。

### 7.3 普通轨道与合伙人轨道互斥

- 首笔实付发生时邀请人仍是普通用户：该来源走一次 `5% + 5%`，以后不得再以同一来源产生合伙人池；
- 首笔实付发生时邀请人已经是合伙人：该来源不再发普通首付奖励，从这笔新来源被实际使用时开始进入合伙人 10% 池；
- 不能同时获得普通首付奖励和合伙人长期分润。

每个付费来源必须在创建时锁定且只能锁定一种策略：

```text
NONE
ORDINARY_FIRST_PAID
PARTNER_USAGE
```

邀请人以后升级、暂停或修改链接，都不能把已经锁定的旧来源改到另一条轨道。

### 7.4 合伙人状态变化

内部状态至少区分：

```text
applying -> active -> suspended -> active
                              \-> terminated
```

- `suspended` 期间，客户已经承诺的返利率继续执行；
- 合伙人份额进入冻结佣金，不进入可提现；
- 恢复后可释放冻结佣金；
- 确认欺诈时，用带原因和审核人的冲销分录处理；
- `terminated` 后只停止未来合伙人现金份额，不追溯没收没有争议的已成熟佣金；
- 直属关系不删除、不转卖、不静默改绑；
- 所有状态变化必须记录生效时间、原因、操作者和证据。

## 8. 普通用户升级后的历史直属客户

合伙人开通时间记为 `activated_at`。

### 8.1 不回算

- 开通前已经购买的余额批次不参与合伙人长期分润；
- 开通前已经购买的月卡权益不参与合伙人长期分润；
- 即使这些旧额度在开通后才使用，也不补算。

### 8.2 开始计算

- 开通后新兑换的实售余额卡，创建新的可分润余额批次；
- 开通后新兑换的实售月卡，创建新的可分润月卡权益周期；
- 历史直属客户默认使用 `客户 0% / 合伙人 10%`；
- 以后新通过合伙人链接绑定的客户，使用链接当时的比例快照。

### 8.3 余额批次 FIFO

余额不能只保存一个总数。每笔来源建立独立 `balance_lot`：

```text
source_type / source_id / source_key
sale_or_redeem_at
original_amount
remaining_amount
affiliate_policy
direct_partner_id
rate_version
```

消费按 `sale_or_redeem_at, id` 先进先出。一次调用跨越新旧批次时，按批次拆分。

例：

```text
开通前剩余 ¥30
开通后新买 ¥50
随后消费 ¥40
```

只有新批次中的 ¥10 进入合伙人分润池。

### 8.4 链动时间边界

链动没有支付回调，当前系统无法知道外部准确付款时间。正式会计政策定义为：

> 卡密在老实人 AI 成功兑换、被系统标记为已售的时间，就是本站的销售确认时间。

因此“外部先买、开通后再兑换”的卡，会按兑换时点处理。除非以后获得可信 `paid_at` 或订单对账数据，否则不得伪造精确付款时间。

## 9. 月卡确认消费

每张月卡创建独立权益周期：

```text
product_sku
actual_sale_price
credit_limit
used_credit
starts_at / ends_at
affiliate_policy
direct_partner_id
rate_version
pricing_table_version
```

确认消费使用整数定点比例：

```text
累计确认消费 =
floor(实付价格 × min(已用积分, 总积分) / 总积分)
```

本次增量只取“新累计值 - 旧累计值”。最后一次用满必须把累计确认消费闭合到实付价格，不能因逐笔舍入超过售价或永久少一截。

## 10. 上下级与防套娃

假设：

```text
A 邀请 B
B 邀请 C
```

即使 B 后来成为合伙人：

- B 自己的新合格来源仍按 A 当时对 B 生效的直属策略给 A 分润；
- C 的消费只给 B 分润；
- A 不从 C 获得第二层佣金；
- B 不从自己的消费获得佣金；
- 一笔消费只有一个 `direct_partner_id`；
- 不按间接人数、间接业绩或层级差计算收益。

技术约束：

- 禁止递归分润；
- 禁止自佣；
- 禁止关系环；
- 同设备、同支付身份、同收款身份、异常 IP/注册速度只作为风险信号，不能自动没收；
- 风险审核期间，新佣金进入冻结余额，不进入可提现；
- 确认欺诈后使用审计冲销，不删除原记录。

“当时生效的直属策略”含义如下：

- 如果 A 从 B 首付前已经是合伙人，B 的该来源按绑定比例进入 A 的长期池；
- 如果 A 在 B 首付后才升级，B 的旧来源仍保持普通首付策略或无奖励；
- A 升级后 B 新购买的来源，按“历史直属客户默认 0% / 10%”进入长期池。

## 11. 佣金成熟、转换与提现

### 11.1 T+0 成熟

客户真实消费确认后：

- 客户返利 T+0 写入平台额度；
- 合伙人现金佣金 T+0 写入可提现佣金；
- 页面每 5 秒刷新摘要；
- 可见明细按“合伙人 + 客户 + 北京日期”聚合，不按 API 调用展示一行。

### 11.2 佣金转平台额度

```text
¥1 可提现佣金 -> ⚡1.2
```

- 转换立即完成；
- 不可撤销；
- 转换所得不可提现；
- 转换所得不可再次触发联盟奖励；
- 转换与提现共用同一可用余额锁，不能并发双花。

### 11.3 提现

- 默认最低 ¥100，后台可配置；
- 用户可申请部分或全部可提现金额；
- 同一合伙人同时只能有一笔处理中提现；
- 提交后金额从“可提现”原子转入“处理中”；
- 用户不能取消；
- 用户侧只显示 `处理中 -> 已到账`；
- 管理员打款失败时，处理金额原子退回可提现余额；
- 24 小时 SLA 按北京时间；
- 管理员必须填写不可重复或可核验的打款参考号；
- 高额提现阈值可配置，超过阈值要求第二次确认。

每笔提现必须有：

```text
withdrawal_id
idempotency_key
requested_amount
reserved_ledger_entry_id
payout_reference
reviewed_by / paid_by
requested_at / paid_at
```

管理员重复点击、页面超时重试或接口重放都只能命中原提现单，不能再次扣款或再次记账。

### 11.4 内部钱包分录

钱包使用不可变流水：

```text
commission_earned
withdrawal_reserved
withdrawal_paid
withdrawal_released
commission_converted
commission_reversed
tax_withheld
```

余额是流水汇总结果，不允许直接改一个 `balance` 数字修账。

## 12. 退款、退款后已消费与打款后冲销

真实退款或确认无效销售时：

1. 创建指向原业务事件的 reversal；
2. 尚未使用的平台奖励直接扣回；
3. 已使用的平台奖励进入负向待抵扣余额或风险审核；
4. 尚未提现的佣金直接冲减；
5. 提现处理中先阻止打款并释放/冲减；
6. 已经打款的佣金形成合伙人负余额，后续佣金优先抵扣；
7. 不删除原奖励、佣金或提现记录。

退款冲销必须有唯一键：

```text
reversal:{original_event_id}:{reason_version}
```

## 14. 新月卡最终建议参数

### 14.1 名称与展示

只显示：

- `Plus`
- `Pro`
- `Max`

不显示 `1× / 5× / 20×`，不设每日额度，只显示月度总额度、有效期、剩余额度和到期时间。

### 14.2 审查后的安全额度

当前生产只读成本核算在 2026-07-28 北京时间观测到，现有月卡最坏活跃路线成本约为每内部原始积分 ¥0.5299。审查采用向上取整后的 ¥0.53，而不是先前的 ¥0.50。

同时，若 10% 合伙人现金佣金全部按 1.2 倍转换为平台额度，最坏联盟负担应按 12% 压测，而不是只按 10% 压测。

因此建议把此前 `2,400 / 7,000 / 15,500` 修正为：

| 套餐 | 月度积分 | 直售价 | 链动价 | 基础最坏直售毛利 | 基础最坏链动毛利 | 再扣 2% 储备后的最坏链动毛利 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Plus | `2,200⚡` | ¥249 | ¥259 | 41.17% | 39.98% | 37.98% |
| Pro | `6,500⚡` | ¥699 | ¥729 | 38.72% | 37.74% | 35.74% |
| Max | `14,000⚡` | ¥1,499 | ¥1,549 | 38.50% | 37.10% | 35.10% |

最坏口径：

```text
当前保守成本：¥0.53 / 内部原始积分
用户展示额度：内部积分 × 10
链动费率：3%
联盟最坏负担：12%
退款、支付、舍入和运营波动储备：2%
最低允许毛利：35%
```

表中毛利统一以商品含税前标价为分母，链动 3% 作为渠道成本扣除。高档直售每单位积分相对 Plus 更便宜，Max 仍低于 ¥1,500。

在当前最坏观测成本不高于 ¥0.53 的前提下，三档即使再扣 2% 储备仍高于 35%；其中 Max 仅剩约 0.10 个百分点，属于硬边界而非宽松安全垫。因此：

- 每次生成新卡密前重新读取当前配置的保守单位成本；
- 压力毛利小于 35% 时，禁止生成新卡；
- 已售卡权益不减损；
- 成本上升时优先减少下一版本积分，不暗改当前周期倍率。

### 14.3 周期

- 每张月卡 31 天；
- 未使用额度到期失效，不结转；
- 不自动续费；
- 同套餐提前续费进入排队周期，不与当前周期额度混算；
- V1 不开放中途升降档，避免两个活动权益重叠和重复归因；
- 以后单独设计“按剩余实付价值折算”的升级流程。

### 14.4 固定计费表

- 所有月卡共用公开计费表；
- GPT 目标公开倍率为 0.50；
- 其他模型使用审核后的固定公开倍率；
- 每个权益周期记录 `pricing_table_version`；
- 当前周期不追溯修改；
- 成本变化时只调整新 SKU 的额度/价格或发布新计费表版本；
- 已生成未兑换卡密保存自己的 SKU、额度、价格和组快照，不能被目录静默改写。

## 16. 税务与规则合规上线门

5. 合伙人协议明确只有一级直属推广，不收入门费、不承诺收益、不按间接层级计酬。

- Staging 可完整测试；

- 不开放真实现金提现。

## 17. 模式、迁移与切换

模式：

```text
off -> shadow -> live
```

- `off`：不记录联盟表现，不产生资金；
- `shadow`：计算并写诊断，不产生奖励、佣金或余额；
- `live`：只处理 `started_at` 之后的合格事件；
- `started_at` 一旦进入 live 永久锁定；
- `live -> shadow/off` 只停止新结算，不删除已产生流水。

迁移要求：

- 从空数据库完整迁移；
- 重跑幂等；
- 所有唯一键、外键、金额非负/比例和约束测试通过；
- 旧 Agent 表只读保留，不承接 V3 新事件；
- 新 SKU 使用不可变代码，不覆盖历史商品。

## 18. 必测场景

### 18.1 普通邀请

- 邮箱注册；
- Gmail OAuth；
- 无邀请码；
- 无效邀请码；
- 自我邀请；
- 重复回调/重复兑换；
- ¥20 / ¥50 / ¥100 余额卡；
- Plus / Pro / Max；
- 礼品/补偿/测试卡不奖励；
- 邀请人与被邀请人各 5%，没有固定 5。

### 18.2 合伙人

- 两条资格路线；
- 路线 A 只累计达到 ¥20 单人门槛的直属用户消费；
- 路线 B 只统计本人消费，直属消费不能帮助达标；
- 达标后仍需人工审核；
- 历史直属绑定保留；
- 开通前余额不分润；
- 开通后新余额分润；
- 一次调用跨新旧批次；
- 历史直属默认 0/10；
- 新链接 0/10、3/7、5/5、10/0；
- 比例修改只影响新绑定。

### 18.3 层级

- A -> B -> C；
- B 成为合伙人后 B 自己消费给 A；
- C 消费只给 B；
- A 不从 C 获得收益；
- 环路和自佣被拒绝；
- 小号风险冻结不影响无辜客户已承诺返利。

### 18.4 钱包

- T+0 成熟；
- 转换 1.2x；
- 转换与提现并发；
- 重复提交提现；
- 部分提现；
- 打款成功；
- 打款失败退回；
- 退款发生在未提现/处理中/已打款之后；
- 负余额后续抵扣。

### 18.5 月卡

- 无每日额度；
- 31 天周期；
- 用量为 0%、部分、100%；
- 最后一笔舍入闭合；
- 提前续费排队；
- 当前周期计费表锁定；
- 旧库存不被新目录修改；
- 35% 压力门拒绝危险配置。

### 18.6 权限与隐私

- 合伙人只能看自己的直属用户；
- 邮箱/账号必要脱敏；
- 无权限访问收款码返回 403；
- 有权限访问成功且有审计；
- 构造跨用户 ID 不能越权；
- 日志和前端不泄露收款账号、二维码对象路径或密钥。

## 19. 监控和财务对账

每日北京时间任务：

- 首付奖励总额；
- 合伙人客户返利总额；
- 现金佣金新增、转换、提现、冲销；
- 各 SKU 实售额、确认消费和实际上游成本；
- 未关联销售；
- 负钱包和超时处理中提现；
- 奖励池占实售额比例；
- 实际毛利和压力毛利。

告警：

- 任意 SKU 压力毛利 < 35%：禁止新发卡；
- 实际毛利连续异常：人工复核，但不追溯减损已售权益；
- 单用户/设备/支付身份高频首付；
- 同一打款参考号重复；
- 提现处理超过 24 小时；
- 资金事件与钱包汇总不平。

真实现金账本与成本核算必须分开：

- 实际收到链动收入按扣除 3% 后入财务账；
- 实际支付宝佣金打款在成功时记现金支出；
- 尚未打款佣金属于内部应付负债；
- 上游充值现金与请求发生的实际上游成本不能混为同一时间口径。

## 20. 审查结论

### 20.1 发现并关闭的高风险问题

| 风险 | 原方案问题 | 本稿关闭方式 |
| --- | --- | --- |
| 重复奖励 | 普通首付奖励与长期分润可能作用于同一来源 | 来源批次记录 `affiliate_policy`，两条轨道互斥 |
| 老余额回算 | 只按消费时间会让升级前余额产生新佣金 | 余额批次 FIFO，按购买/兑换来源判断 |
| 自购后申请套利 | 本人达到 ¥500 后申请，可能只为取得现金推广资格 | 只获得申请权、必须人工审核，且本人消费永不自返佣 |
| 多层套娃 | B 升级后可能同时让 A、B 对 C 抽成 | 每笔只允许一个直属合伙人，不递归 |
| 佣金转换漏算 | 10% 现金转 1.2x 后最坏负担是 12% | 毛利门按 12% 压测 |
| 成本假设偏低 | 原来按 ¥0.50/原始积分 | 使用当前只读观测最坏值向上取整 ¥0.53 |
| 提现双花 | 转换与提现可能同时使用同一余额 | 钱包行锁、不可变流水、单处理中提现 |
| 退款后已打款 | 已提现佣金无法直接删除 | reversal + 负余额 + 后续抵扣 |
| OAuth 丢邀请 | 第三方登录跳转会丢查询参数 | 签名短期 Cookie，创建账号时原子绑定 |
| 收款码泄露 | 公开对象 URL 或只靠前端隐藏 | 鉴权下载、加密、审计、越权测试 |
| 记录爆炸 | 每次 API 调用生成用户可见行 | 请求级审计 + 每客户每日聚合 |
| 月卡追溯变价 | 修改分组倍率会减损已售权益 | 权益锁计费表版本，新周期才变 |
| 舍入穿透 10% 池 | 两侧独立四舍五入可能合计超过总池 | 先算总池、再拆分、尾差单列 |
| 合伙人停用伤及客户 | 暂停合伙人可能连带取消客户既有返利 | 客户返利继续，合伙人份额先冻结 |
| 人工重复打款 | 页面重试可能导致两次扫码、两次入账 | 提现幂等键、唯一参考号和双人高额确认 |
| 运营杂费吃穿毛利 | 原压力表未单列支付/退款/舍入波动 | 额外扣 2% 储备，卡密生成前再过 35% 门 |

### 20.2 仍然存在但已明确控制的外部边界

1. 链动无支付回调：只能以卡密兑换时间确认销售；这是会计政策，不伪装成精确付款时间。
2. 多账号不能只靠技术完全识别：通过真实付费、单池上限、无递归收益和人工风险审核，把收益上限压到正常折扣范围。
3. 个人现金佣金税务处理需要专业确认：在确认前禁止生产现金 live。

### 20.3 最终判断

在采用本稿修正后的参数和约束后：

- 没有发现能够让一笔真实消费生成超过一个联盟池的技术路径；
- 没有发现无需真实付费即可凭空产生可提现现金的路径；
- 没有发现通过升级合伙人制造多级递归佣金的路径；
- 最坏资金负担下三档月卡压力毛利率均高于 35%；
- Staging 可以进入实现阶段；
- 生产现金功能仍受税务确认和所有者明确上线批准双重限制。

## 21. 实施顺序与每阶段存档点

没有得到所有者对本稿的明确确认前，不进入以下实现。

### 阶段 0：冻结规则与测试向量

- 把本文关键公式转成机器可读测试向量；
- 固定术语、SKU、比例、时间口径和业务唯一键；
- 删除旧文档里固定 `⚡5`、T+1、自动升级、旧月卡价格的冲突描述。

验收：同一个例子由产品文档、后端测试和前端展示算出同一结果。
存档点：`docs(affiliate): freeze v3 financial rules`

### 阶段 1：迁移与不可变账本

- 新增策略枚举、比例版本、状态时间线、钱包分录、冲销和提现字段；
- 补齐唯一约束、检查约束、外键和必要索引；
- 旧表只读兼容，不让旧 Agent 逻辑写入新账本。

验收：空库迁移、已有 Staging 数据迁移和重复迁移全部通过。
存档点：`feat(affiliate): add v3 ledger schema`

### 阶段 2：邀请绑定与登录链路

- 邮箱注册、邀请码注册、Gmail OAuth 都走同一原子绑定服务；
- 关闭优惠码 UI 和接口入口；
- 加入自邀、环路、重复回调和篡改 Cookie 测试。

验收：三种注册路径绑定结果一致，OAuth 不丢邀请码。
存档点：`feat(affiliate): harden referral binding`

### 阶段 3：普通用户首付奖励

- 实现 `5% + 5%`、T+0、无固定 5；
- 余额卡和月卡都写来源策略；
- 礼品、补偿、测试、迁移、转换额度全部排除。

验收：重复兑换、并发回调和重试不重复奖励。
存档点：`feat(affiliate): settle first-paid rewards`

### 阶段 4：合伙人申请与审核

- 实现路线 A（5 人、每人 ≥ ¥20、有效直属合计 ≥ ¥1,000）；
- 实现路线 B（仅本人确认消费 ≥ ¥500）；
- 增加资料审核、收款资料权限、社群二维码和状态时间线。

验收：达标不会自动开通，越权读取收款码被拒绝且留审计。
存档点：`feat(affiliate): add partner application review`

### 阶段 5：消费归因与动态 10% 池

- 余额批次 FIFO；
- 月卡按使用比例确认消费；
- 历史直属、新直属、比例快照、跨批次和 A-B-C 场景全部落地；
- 用户可见记录按客户和北京日期聚合。

验收：每个资金事件最多一个直属合伙人，总分配不超过所属池。
存档点：`feat(affiliate): settle direct usage commissions`

### 阶段 6：佣金钱包、转换、提现与冲销

- T+0 成熟；
- 1.2 倍转换；
- 提现预占、打款、失败释放、退款后负余额；

验收：转换/提现并发压测无双花，重复管理操作无重复打款记录。
存档点：`feat(affiliate): add withdrawal ledger workflow`

### 阶段 7：月卡目录 V3

- Plus / Pro / Max；
- 31 天、无日限额、固定计费表版本；

验收：当前三档公式、到期、续费、旧库存兼容全部通过。
存档点：`feat(monthly): add guarded plus pro max catalog`

### 阶段 8：前端与运营后台

- 合伙人中心只保留一套联盟入口；
- 邀请用户、分润、申请、转换、提现和状态展示；
