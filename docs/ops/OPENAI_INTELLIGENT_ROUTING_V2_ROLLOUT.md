# OpenAI 智能路由 V2 Shadow 活动与复评协议

本文定义代码合并以后仍然必须遵守的运行状态机。当前分支只准备能力，**没有创建
生产定时任务、没有写 Shadow 策略，也没有改变真实账号选择**。

主动半开探针同样保持硬关闭：`OpenAIRouteActiveProbesCodeAvailable=false`，runner
没有接入 Wire、扫描器、cron 或网络 client。它只准备 route 到期判断、进程内去重、
Redis 单主租约/续租、失租取消和独立统计；不得把主动结果写入真实用户的被动观测。

## 不可越过的状态机

```text
code_ready_legacy
  -> separately_authorized_shadow
  -> checkpoint_24h
  -> primary_review_72h
  -> manual_review
  -> explicitly_authorized_1_percent_canary (future release only)
```

任何状态都不能自动跨越到下一档真实流量。当前版本继续硬禁止 `enforce`，因此即使
72 小时全部自动证据通过，也只会返回 `consider_1_percent_canary`，不会执行它。

### 0. Code ready / Legacy

- 合并、迁移和部署后，策略保持缺失、`enabled=false` 或 `mode=legacy`。
- 验证服务健康、Redis/审计表可用和 Legacy 行为没有改变。
- 此状态不能预先创建以“预计部署时间”为起点的 72 小时任务。

### 1. Separately authorized Shadow

只有获得一次明确的生产 Shadow 授权后，才可以写入版本化策略。启用时必须记录：

- UTC 的真实 `shadow_started_at`，向老板汇报时换算为北京时间；
- 本轮不可复用的 `activation_id`；停用再开必须换新 ID；
- `group_id + model + request_class + policy_version` 完整切片；
- 归一化策略快照和操作者；
- 24 小时检查点与 72 小时主评估的绝对时间。

策略开启后仍由 Legacy 选择真实账号。Shadow 只计算、审计和被动学习。

### 2. 一次性复评任务

仅在真实 Shadow 起点存在后，通过 Codex 自动化能力创建两个**一次性唤醒任务**：

1. `T0 + 24h`：健康检查点；
2. `T0 + 72h`：主评估。

任务只唤醒本 Codex 工作任务并执行只读查询，不携带生产凭证，不修改策略。若 72
小时评估未通过，则保持 Shadow，并从本次评估时间起安排 `+24h` 的下一次只读复评；
不得用周期 cron 自动改参数或自动晋级。所有时间按 UTC 存储，按北京时间汇报。

## 24 小时检查点

这是早期止损检查，不是晋级门禁：

- 审计 `attempted = written + failed + in_flight`，排空后 `in_flight=0`；
- 审计与被动采集计数器的实例启动时间均不晚于 T0；观察期内重启会使当前切片失效；
- 两类存储探针从计数器启动后保持零失败；恢复后的成功探针不能覆盖历史证据空档；
- 审计写入完整率、被动采集完整率和健康状态应用完整率均不低于 99%；
- 审计与被动采集使用有界异步队列，队列拒绝、丢弃、失败和尚未完成的任务都必须
  进入完整率分母，不能用“后来一次成功”掩盖早先丢失的证据；
- Shadow 评估 P95 开销没有挤占用户请求截止时间；
- 失败分类、文本/图片身份和故障域没有串线；
- 未出现应急预算、策略版本复用或异常集中度。

检查失败时继续走 Legacy；必要时关闭 Shadow 策略以移除评估开销，但不得删除历史
审计。修复必须走新的代码审查或新策略版本，不能原地掩盖旧证据。

## 72 小时主评估

调用精确切片的 `GET /api/v1/admin/ops/openai-route-shadow/assessment`，固定
`start_time=T0`、`end_time=T0+72h`，并显式携带本轮 `activation_id`。自动门禁至少包括：

- 数据库切片只有一个非空 activation 和一个非空 T0，且 `window_start` 精确等于
  持久化 T0；历史行、前一轮启用或停开后的同版本证据都不能混入；
- 查询窗口达到 72 小时；实际首末决策跨度至少 71 小时，即右边界不包含在查询结果
  且真实流量不与边界同步时，两端合计只允许最多 1 小时空档；延期复评若使用更长
  窗口，同样只允许合计 1 小时空档；
- 仅以有效评估计算相对 T0 的小时桶，72 小时窗口至少覆盖 71 个桶；延期窗口也只能
  缺一个桶。首末时间合格但中间长时间无数据时必须阻止晋级；
- 至少 200 条有效评估，评估和真实结果关联完整率均不低于 99%；
- 无歧义结果、无应急预算、策略快照唯一；
- 建议账号和建议故障域的计数都完整覆盖全部有效评估；
- 账号与故障域建议集中度不超过策略上限；
- 审计、被动采集和健康写入均 Ready。
- 两类进程内完整率计数器都覆盖完整窗口；多实例部署逐实例核验，不能把单实例响应
  当成集群完整率。
- 审计与观测存储探针在计数器生命周期内均无失败记录。

Shadow 决策审计写库不能位于账号选择热路径。运行时只允许把不可变快照提交给有界
队列；队列满时继续由 Legacy 服务用户，并把该决策计为丢失证据。客户端主动取消的
请求可用于统计请求量，但不能进入可靠性、延迟或半截流评分，不能触发线路熔断或
升级供应商故障域。

自动门禁通过后仍需人工核验：权威上游账单、Legacy 可比基线的错误率与恢复率、
P95/P99 TTFT/完成延迟、文本粘性/图片无粘性，以及老板授权。

## 每轮自我复盘模板

每次 24/72 小时或延期复评都必须留下同一结构的结论：

1. **范围**：北京时间窗口、完整策略切片、代码提交和策略版本；
2. **数据质量**：总数、有效数、关联率、歧义、丢弃、写入失败和缺失时段；
3. **用户体验**：按账号、故障域、模型、传输和北京时间周内小时比较成功率、TTFT、
   完成延迟、半截流和切换；
4. **成本校准**：策略先验、候选预测、权威文本结算均值和误差；图片不得由 token
   样本反推供应商成本；
5. **算法偏差**：检查 Legacy 选择偏差和候选覆盖。Shadow 未实际执行建议账号，
   因而不能把 Legacy 结果冒充为反事实结果；
6. **故障域**：确认同供应商 Base URL 相关失败没有被当成独立冗余；
7. **结论**：只能是继续采集、修复后重开新版本、关闭 Shadow，或申请人工评审；
8. **下一步**：明确下一次只读复评时间、代码 PR 或需要老板决定的事项。

线上统计不能直接自动改权重、份额上限或熔断阈值。算法变更必须带离线重放/测试、
新 `policy_version` 和可回滚审计，防止反馈回路把一次偶发异常放大成持续抖动。

## 回滚

- Shadow 阶段：`enabled=false` 或 `mode=legacy`，清设置缓存；真实路由本来就未接管。
- 未来 Canary：需要独立实现确定性桶和一键 Legacy 回滚，且不得与首次 Enforce 代码
  在同一次发布启用。依赖分支已经准备 `1% -> 5% -> 20% -> 50% -> 100%` 的纯合同，
  但编译期 `OpenAIRouteEnforceCodeAvailable=false`，也没有接入真实 scheduler；因此它
  只能测试 cohort 和转移不变量，仍不能切流。
- 回滚只停止新决策，不删除 Shadow 决策、聚合检查点或复评记录。
