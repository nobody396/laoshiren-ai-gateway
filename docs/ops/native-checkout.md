# 链动小铺原生结账运行手册

## 目标与边界

原生结账让已登录用户在老实人AI站内选择商品、扫描链动小铺当前启用的微信或支付宝付款码，并在支付完成后自动获得权益。链动小铺负责收款和发卡；老实人AI数据库负责账号级限购、订单幂等、卡密校验和自动兑换。

首个试点的最终口径为实付 ¥5、到账 ¥10 **纯赠送余额**，每个账号终身仅一次。迁移 188 写入唯一的业务配置行 `newcomer-balance-5-to-10`；数据库 offer 行是名称、价格、到账金额、卡密语义和终身限购的唯一事实源。前端只渲染 API 返回值，运行手册不作为可执行配置。对应链动商品 ID `746430`、goods key `oc3w4r`，保持 `show=0`，不在小铺目录公开。

本地 Docker 只用于付款前的预览和真实链路验收。正式订单、轮询、取码和兑换都由生产服务器上的 `sub2api` 应用进程执行，状态持久化到生产 PostgreSQL；用户关闭网页或更换设备不会中断履约。

## 安全不变量

- 只使用当前登录账号的注册邮箱下单；订单表仅保存域隔离的 HMAC，不复制邮箱正文。
- `native_checkout_orders` 的部分唯一索引是每账号一次的唯一权威。不要开启链动侧按 IP/联系方式限购，因为所有买家请求来自同一服务端出口。
- 支付后必须同时校验交易号、商品 key、联系方式、数量、实付金额、发货数量和卡密权益。
- 当前试点卡必须与 offer 行完全一致，即 `type=balance`、`value=10`、`paid_value=0`、`purpose=gift`、`sales_status=gifted`、`validity_days=0`。数据库触发器会拒绝任何不匹配的库存登记，并禁止已备货 offer 改写权益语义。
- 已上传链动的原生结账库存必须预先登记到 `native_checkout_redeem_inventory`。公开手动兑换接口会拒绝这些卡，只有已绑定订单的站内履约路径可兑换。
- 即使付费订单是在原生订单表之外恢复，只要对应原生库存卡已由该账号使用，也必须计为该账号已领取一次，不能重新开放购买按钮。
- 不记录完整卡密、注册邮箱、付款 URL 或链动交易号到日志。
- 下单时只接受链动返回的 `WeixinNative` 或 `Alipay` 活跃扫码通道，并把实际选中的通道固化为订单的 `payment_method`。前端必须按订单值提示“打开微信扫码”或“打开支付宝扫码”，不得从商品当前配置或付款 URL 猜测。
- 只有服务端履约任务查询链动订单状态和发货内容；浏览器每 3 秒读取的只是老实人AI数据库中的订单状态，不会触发链动订单查询。打开支付弹窗时仍会按需获取一次付款二维码。链动官方买家前端也是每 3 秒查询 `/shopApi/Pay/query`，当前未发现可配置的可靠付款 Webhook。
- 匿名 `/shopApi/Order/info` 详情稍后可能要求买家重新输入联系方式并通过人机验证。生产必须通过部署 secret 注入 `LDXP_MERCHANT_USERNAME` / `LDXP_MERCHANT_PASSWORD`，使后台在匿名详情不可用时自动改走商户订单详情；商户 token 仅在进程内缓存。匿名详情或商户接口出现 403/429 时必须熔断 10 分钟，不能形成重试风暴。
- 链动创建订单响应与订单详情目前都不返回明确失效时间。前端只显示“建议 10 分钟内支付”，不宣称这是支付渠道的硬失效时间；实际是否仍可付款以微信或支付宝支付页为准。

## 并发与自动履约

- 同一账号同时点击多次时，数据库唯一索引只允许一个 `user_id + offer_code` 终身订单；竞争失败的请求读取并返回同一订单，不会再向链动创建第二个订单。
- 不同账号各自持有独立站内订单和链动交易号，可以同时下单、付款和到账。同一时刻购买同一商品的请求会合并商品与支付通道元数据查询，但每位用户仍单独创建自己的可付款订单；单个应用实例最多同时向链动创建 8 个订单，超过部分在请求上下文内排队，避免无上限冲击上游。
- 服务端每秒扫描到期任务，每次通过 PostgreSQL `FOR UPDATE SKIP LOCKED` 原子领取最多 4 个订单并设置 30 秒租约。即使以后运行多个应用副本，同一订单同一时刻也只会由一个副本查询链动；执行器异常退出后租约到期即可恢复。
- 未付款订单在创建后 2 分钟内每 3 秒核对，随后按 10 秒、30 秒、5 分钟、1 小时逐级降频，避免遗留二维码永久高频占用链动接口；已确认付款但等待发码的订单保持快速核对。
- 链动返回发货码后，服务端依次校验订单身份与权益、原子占用受限库存卡、绑定链动交易号、调用事务型兑换服务并完成订单。兑换码状态和用户余额在同一数据库事务中更新；任何进程中断都从持久状态幂等恢复，不依赖用户页面保持打开。

## 发布门

商品目录展示只读本地 offer，避免每次打开充值页都请求链动。真正下单前仍会用该 offer 行重新校验链动商品状态、¥5 金额、联系方式格式和实际支付通道；校验失败不会返回可付款订单。因此代码合并或应用部署不等于开售。迁移 189 会把 `newcomer-balance-5-to-10` 保持为 `enabled=false`，避免应用部署先于链动商品和库存准备时向用户暴露不可履约入口。

开售前依次确认：

1. 数据库迁移成功，`newcomer-balance-5-to-10` 行精确回读为实付 500 分、到账 1000 分、终身限购、`enabled=false`。
2. `native_checkout_redeem_inventory` 中符合当前 ¥10 纯赠送语义的未分配库存，与链动商品卡密库存逐张一致；所有不符合当前 offer 的卡必须先从链动商品移除，且数据库触发器必须拒绝登记。
3. 链动商品已改为 ¥5、邮箱联系方式、隐藏展示、链动侧限购为 0，且微信 Native 或支付宝扫码渠道至少有一个可用。
4. 应用健康与鉴权边界正常后，再将链动商品设为 `status=1`，保持 `show=0`；精确回读商品金额、库存和当前扫码通道。
5. 最后在生产数据库单行启用 `newcomer-balance-5-to-10`，并回读确认 `enabled=true`。不要在前四项完成前启用 offer。
6. 使用测试账号完成一次真实小额支付，确认站内自动到账 ¥10，第二次点击不新建订单。
7. 等待匿名订单详情要求重新查询后，验证商户 API 兜底仍能取得同一张卡并幂等完成；正常支付并发卡后预计 3–15 秒到账。

任一校验失败，先把站内 offer 设为 `enabled=false`，再将链动商品设为 `status=0`。不要删除订单或库存记录。

## 补库存

补货必须使用新的稳定批次引用生成纯赠送卡，先将全部 code ID 和 offer 原子登记到 `native_checkout_redeem_inventory`，精确回读后才可上传链动。禁止先上传再登记，也禁止把完整卡密写入仓库、日志或聊天。库存数量以生产数据库与链动后台的逐张回读为准，不在文档中固化。
