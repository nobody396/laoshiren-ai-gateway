## 2. Executive finding

**The OpenAI-platform gateway has a P0 contract hole:** it registers both `POST /v1/images/generations` and `POST /v1/images/edits`, but the shared OpenAI handler only accepts a JSON body of at most 1 MiB, has no endpoint/content-type/upload representation, rejects streaming, and the forwarder always targets `/v1/images/generations`. Therefore the registered OpenAI `/images/edits` route does not implement image editing; standard single-image multipart, `mask`, and `image[]` multi-image requests cannot work correctly. See the local `backend/internal/server/routes/gateway.go:58-64 @ 00fdebf`, `backend/internal/handler/openai_images.go:18-68 @ 00fdebf`, `backend/internal/service/openai_images.go:73-81 @ 00fdebf`, `backend/internal/service/openai_images.go:124-187 @ 00fdebf`, and `backend/internal/service/openai_images.go:1606-1641 @ 00fdebf`.

This is **not** a total media-gateway absence. Grok groups already dispatch edits separately and convert multipart uploads, multiple images, and a mask into xAI JSON. However, that parser is permissive/fail-open on malformed multipart and reads each file through an exact `LimitReader(20 MiB)` without detecting overflow, so an oversized file can be silently truncated before forwarding. See `backend/internal/service/grok_media.go:194-269 @ 00fdebf` and `backend/internal/service/grok_media.go:604-665 @ 00fdebf`.

The minimum repair should absorb the endpoint-aware, multipart-aware shape used by current Wei-Shaw/Sub2API and the parse-once/rebuild behavior demonstrated by new-api, while **not blindly copying** either project’s limit and validation weaknesses.

## 4. Recommended minimum repair scope

### P0 — one synchronous, contract-correct slice

1. **Make the request endpoint-aware.** Pass request path and content type into the parser; store canonical endpoint (`generations` or `edits`), content type, and multipart flag. Build the matching upstream URL. Do not route edits through a Responses/image-generation bridge unless that bridge explicitly implements edit inputs and mask semantics.
2. **Support the two official edit shapes.**
   - multipart: one or repeated `image`, `image[]`, or indexed `image[...]`, optional `mask`, and all scalar fields;
   - JSON: `images[].image_url` plus optional `mask.image_url` (URL or data URL). Return a clear 400 for `file_id` until a real Files integration exists.
3. **Preserve bytes and fields exactly.** Rewrite only the selected upstream model. For multipart, rebuild a fresh boundary, preserve filenames and detected media types, and forward every recognized scalar field without silently defaulting/removing it.
4. **Add hard safety bounds.** Keep the existing total gateway cap or introduce a smaller image-specific configurable cap, enforce no more than 16 input images and one mask, enforce a per-file cap compatible with the official under-50-MB rule, and read `cap+1` so overflow is rejected with 413 rather than truncated. Apply the cap after decompression. Reject empty files, non-image magic bytes, and undecodable images. For mask requests, reject format/dimension mismatch and a mask without alpha, or deliberately pass these to upstream and preserve its 400—never silently alter them.
5. **Validate only stable cross-model constraints locally.** Require non-empty prompt (max 32,000), `n` 1–10, `output_compression` 0–100, `partial_images` 0–3, and correct JSON/scalar types. Preserve model-specific `size`, `quality`, `background`, `moderation`, `output_format`, `input_fidelity`, `style`, `response_format`, `stream`, and `user`; let the selected upstream return model-specific 400s rather than applying stale allowlists.
6. **Keep billing/failover fail-closed.** A request is billable only after a validated image output or authoritative positive image usage evidence. Count actual completed images, retain input/output/image token details, and keep the current detached upstream context so disconnects cannot evade accounting. Never replay after any response bytes, usage/error evidence, or candidate output. Preserve `x-request-id` and the OpenAI error envelope; do not retry `image_generation_user_error`/`moderation_blocked` as if it were provider capacity.

### P1 — compatibility completion

7. **Proxy Images SSE.** Forward `stream=true` and `partial_images`; count only terminal `image_generation.completed` / `image_edit.completed` outputs; continue draining upstream after client disconnect; bound idle time and response bytes.
8. **Make moderation/ops multipart-safe.** Moderate prompt plus input images/mask without writing raw base64 or uploaded bytes to ops logs. Hash a canonical, non-secret request descriptor for idempotency/stickiness instead of logging the raw multipart body.
9. **Provider isolation.** Reuse the same validated upload structure for Grok, but retain the required xAI multipart-to-JSON transformation. Do not send OpenAI multipart to xAI or xAI JSON to OpenAI merely because both public routes have the same name.

### Required tests before calling the fix complete

- generations JSON: fields preserved, model mapping only, correct upstream path;
- edits multipart: single `image`, repeated `image[]`, indexed images, mask, all scalar parameters, exact filenames/content bytes, fresh boundary;
- edits JSON: 1 and 16 image URLs/data URLs; 17 rejected; `file_id` rejected clearly;
- size safety: exactly at limit accepted, one byte over rejected (no truncation), total body overflow 413, compressed overflow 413;
- validation: prompt/n/compression/partial-image bounds, empty/non-image/undecodable uploads, mask mismatch/alpha behavior;
- response: valid URL and each supported base64 format, empty 200, malformed output, 4xx user error, 429/5xx, SSE partial/completed/error, downstream disconnect;
- billing: no charge before validated completion, actual count overrides requested `n`, input/output/image tokens retained, duplicate request fingerprint charges once, disconnect still settles completed upstream work;
- route isolation: OpenAI edits reaches `/v1/images/edits`; generations reaches `/v1/images/generations`; Grok conversion remains provider-specific.

## 5. Explicitly out of the minimum slice

Do not expand this repair into variations, async tasks, batch images, object storage, Files API upload/download, or new provider onboarding. Current Wei-Shaw/Sub2API has async/batch surfaces, but they do not need to be copied to close the advertised synchronous generations/edits contract. After P0/P1 is green, `file_id`, async and batch can be designed as separate capabilities with their own storage, authorization, expiry and billing invariants.

## 7. Repair branch status

Branch `fix/images-gateway-20260828` implements the synchronous P0 slice without changing public production state:

- endpoint-aware forwarding to either `/v1/images/generations` or `/v1/images/edits`;
- multipart single/multiple image uploads, optional mask, fresh-boundary rebuild, model mapping, and scalar-parameter preservation;
- JSON edit inputs with up to 16 HTTP(S)/data-URL images and an optional mask; `file_id` fails clearly until a real Files integration exists;
- stable prompt/count/compression/partial-image bounds, 50 MiB per OpenAI upload, overflow detection with `limit+1`, decodable-image checks, and mask format/dimension checks;
- account-level edit capability gating, Azure `response_format` omission for both JSON and multipart, correct edit endpoint attribution, and no raw edit bytes in ops request context;
- Grok multipart overflow validation before xAI JSON conversion, removing the previous silent-truncation path.

The implementation deliberately keeps Images SSE, async tasks, batch images, variations, Files API IDs, and new provider onboarding outside this synchronous repair. None of those capabilities should be documented as available until separately implemented and verified.
